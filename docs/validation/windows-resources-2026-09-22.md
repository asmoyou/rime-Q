# 2026-09-22 Windows CPU 与同步资源排查

结论：已证实无变化时重复整库读取，以及相同本机快照重写整个同步基线。当前没有测到持续满核或内存持续增长，但长期后台消耗有明确优化空间。此次只增加诊断工具与证据，未修改、停止或替换现用输入法，未改动个人词库或同步组。

## 实测条件及结果

Windows，Intel Core i5-6600K @ 3.50 GHz，4 个逻辑处理器；已安装 0.4.5.9140。工作区 HEAD 6148a55，产品提交 b8dfa64。香港时间 2026-09-22 14:17:38 起连续 60 秒、每秒采样；进程运行数小时，热缓存。同步开启，2 台在线且均已确认，7,908 条有效记录，前后 revision 相同，无待应用任务。未主动注入按键，不视作受控真实宿主输入测试。

CPU 用进程 CPU 时间增量除以墙钟及逻辑处理器数，采用任务管理器整机口径；本机单核占满为 25%。范围为三个独立进程，不包括宿主内 TSF DLL、系统服务和杀毒软件。

| 进程 | 平均 CPU | 1 秒样本最高 CPU | 工作集 | 私有提交 |
| --- | ---: | ---: | ---: | ---: |
| RimeQ 设置/托盘 | 0.163% | 1.563% | 119.29 MiB | 124.52 MiB |
| RimeQ.Broker 引擎 | 0.020% | 0.391% | 23.32 MiB | 13.99 MiB |
| RimeQ.Sync 同步 | 1.003% | 2.343% | 18.73 MiB | 9.76 MiB |

同步占三进程 CPU 时间的 84.6%；与用户看到偶发 2–3% 相符，但不能推出始终维持 2–3%。同步工作集在该分钟为 18.71–18.73 MiB，尚无持续增长证据。工作集与私有提交不是同一指标；工作集相加可能重复计入共享页。

同步进程该分钟读取计数 299,040,768 字节（285.19 MiB），73,008 次读取，写入仅 4,120 字节。Windows 进程 I/O 包含缓存文件访问、管道等，不能直接解释成物理读盘或网络流量。

## 已确认的浪费

1. **每秒两次完整状态读取。** `windows/settings/Program.cs:97` 每秒调用 Tick；`windows/settings/Sync.cs:78` 用 status 探活，第 131 行立即再次请求 status。打开同步窗口还会增加查询。`sync/src/service.rs:755` 为返回条数调用 `store.rows()?.len()`，`store.rs:686` 扫描 heads、分组并重建全部词条字符串，即使 revision 未变也执行。

   基线结束后另外连续请求 status 20 次：中位延迟 15.93 ms，最大 31.07 ms；同步进程 CPU 共 328.125 ms、逻辑读取 41,328,640 字节。该探针是人为负载，不能把其 23.63% CPU 当成正常后台占用。每秒两次查询足以解释后台 CPU 的大部分量级，但没有采样栈分析，不能精确归因。

2. **取消输入也触发学习变化标记。** `windows/broker/engine.cpp:167` 对 handled 且非 hello 请求增加 learningRevision，包含 clear、toggle 和未上屏拼写。协调器随后导出整库；`engine.cpp:184` 的同步导出关闭会话、导出并预热新会话。生产服务持有引擎互斥锁，可能延迟后续按键，但本轮未测真实宿主阻塞。

   使用已有独立 librime 夹具、临时目录及 7,908 条合成记录，复现 begin → cancel 后 revision 增加、前后导出文件摘要相同。热缓存导出 5 次：中位墙钟 158.03 ms，中位 CPU 125 ms，墙钟范围 147.17–182.82 ms。包含会话重建和预热，不包含 UI/TSF；夹具二进制摘要见 JSON，不将此当作现用 Broker 的现场调用栈。

3. **相同快照仍整表重写。** `sync/src/store.rs:724` 的 capture 已算出 changes，但即使为空，第 767 行仍调用 set_baseline；第 714 行先 DELETE 整表再逐条 INSERT。

   使用已安装 0.4.5 同步二进制，在隔离目录建立 7,908 条合成记录并初次 capture。再提交相同 rows 三次，均未创建应用任务；中位墙钟 133.47 ms、中位 CPU 125 ms，单次进程写入计数 1,734,520–3,458,968 字节（约 1.65–3.30 MiB，含 WAL/检查点差异）。这不是无新输入基线里持续出现的写入，而是可由不必要的 revision 增加触发的成本。

4. **在线且无变化时仍每两秒重连。** `sync/src/service.rs:1306` 成功后两秒再尝试。sync_peer 重新建立 TLS、认证并交换成员/版本/回执，再查询缺失操作。这不等于每两秒传输全量词条，但握手和验证重复发生。失败已有退避，无变化成功路径没有降频。`store.set` 对相同 meta 值已有跳过更新条件，不能误称每次心跳都会落盘。

## 优化顺序

- 合并重复状态查询，协调器用轻量 revision/待应用状态；条数随数据提交缓存，不要仅为显示条数读取完整词库。仅改成 COUNT 仍会扫描，不能代替控制频率。
- 相同本机快照跳过基线重写；实际变更增量更新，保留事务、恢复、应用确认及本机变更保护。
- 无变化联网检查可降至 30–60 秒；实际修改合并到较短窗口，手动同步立即执行。直接延长间隔时也要调整当前 20 秒在线判定，避免误报离线，回归重连与新成员传播。不要削弱身份/签名校验。
- 学习变化依据实际学习、删除、导入等事件；增加防抖和最小导出间隔。不能简单只检测中文上屏，避免遗漏权重、删除和导入。
- 内存重点另查常驻 WPF 设置/托盘宿主，评估按需加载界面。同步约 19 MiB 本身不能证明泄漏；CPU 已有更明确的优先问题。

## 边界与其他检查

模型工作线程每秒检查文件时间，摘要仅在时间变化时重新校验，未发现每秒重算 420 MB 模型 SHA-256。实测 Broker 平均 0.020%，不是本轮主要 CPU 来源。动态候选装饰由输入事件触发短定时器、隐藏时停用，未发现常驻动画循环。TSF 就绪重试定时器在 ready 后仍每 500 ms 唤醒，但不再请求引擎，是次要唤醒开销，不能解释独立同步进程 CPU。

macOS 共用 Rust 同步核心，Swift 协调器也有重复 status 路径；本机无法给出 Mac 实测数值。未做同机同词库的其他 Rime 前端对照；引擎库、前端、同步、设置和宿主 DLL 的统计范围必须一致，不能直接以进程名字横比。

## 证据

- `windows-resources-2026-09-22.json`：60 个每秒样本、汇总及独立状态探针。
- `windows-resource-engine-2026-09-22.json`：合成词库取消输入与导出。
- `windows-resource-capture-2026-09-22.json`：已安装同步二进制的无变化 capture。
- `scripts/diagnose_windows_resources.py`：标准库和 Windows 只读计数 API；控制凭据仅在内存中用于本地 status 认证，不输出凭据、词条、设备身份或地址。传入待测 PID 可复测；`--status-requests 0` 关闭额外状态探针。
